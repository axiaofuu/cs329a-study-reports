# 代码库阅读报告规范

## 目标

读者完成报告后，应能回答：项目解决什么问题、从哪里启动、一次核心流程怎样经过各模块、每个模块接收什么、产生什么、内部怎样实现、失败时会发生什么。

## 证据原则

- 每个结论必须指向文件和行号。无法从代码确认时写“未确认”，不得猜测。
- README 和注释只能说明设计意图；真实行为以实现、配置和测试为准。
- 区分静态推断和实际运行验证。没有执行过的路径不能写成“已经验证”。
- 不复制 `.env`、密钥、令牌、Cookie、私钥或用户数据。只记录配置变量名和用途。
- 第三方依赖只解释项目实际调用的部分，不展开整个依赖库。

## 每个模块必须回答的问题

1. **作用**：它负责什么，不负责什么。
2. **入口**：哪些文件、函数、命令、路由或事件会进入该模块。
3. **输入**：参数、请求、文件、环境变量、数据库记录或消息。
4. **输出**：返回值、HTTP 响应、文件、数据库修改、消息或副作用。
5. **实现方法**：按执行顺序解释核心步骤。
6. **依赖**：它调用哪些内部模块和外部库。
7. **调用方**：谁会使用它。
8. **状态与副作用**：缓存、数据库、文件系统、网络和全局状态。
9. **失败方式**：错误如何产生、传播、重试或被吞掉。
10. **测试证据**：哪些测试覆盖该模块，哪些关键路径没有测试。

## 解释顺序

先讲一次具体调用怎样流动，再定义架构名称。先解释“谁调用谁、数据怎样变化”，再使用 controller、service、repository、adapter、middleware 等术语。

每段只解释一个动作。复杂实现拆成编号步骤：

```text
接收输入 → 校验 → 转换 → 调用依赖 → 保存状态 → 返回结果
```

## 架构报告必须包含

- 项目目的、技术栈和运行环境。
- 目录与模块地图。
- 启动入口和初始化顺序。
- 至少一条端到端核心调用链。
- 每个核心模块的输入、输出和实现方法。
- 数据模型、持久化和状态变化。
- 配置、构建、测试和部署流程。
- 错误处理、并发、缓存和安全边界。
- 已确认事实、合理推断和未确认问题的明确区分。

## 禁止写法

- “该模块负责业务逻辑”而不说明具体业务动作。
- “提高性能”“增强扩展性”而没有代码路径或测量证据。
- 只复述目录名、类名和函数名。
- 把类型签名当作完整实现解释。
- 根据文件名猜测运行时行为。
- 省略副作用、异常路径和隐式配置。
